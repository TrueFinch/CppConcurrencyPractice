# Базовая задача: Классический пул потоков (Basic Thread Pool)
## Цель

Создать пул потоков фиксированного размера с единой thread-safe очередью задач и поддержкой получения результатов через std::future.
Требуемый интерфейс

```c++
class ThreadPool {
public:
// Создает threads_count рабочих потоков
explicit ThreadPool(size_t threads_count = std::thread::hardware_concurrency());

    // Корректно завершает работы: дожидается выполнения оставшихся задач
    ~ThreadPool();

    // Запрет копирования/перемещения
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;

    // Принимает любую функцию/лямбду с любыми аргументами,
    // возвращает std::future с результатом ее выполнения
    template <typename F, typename... Args>
    auto push(F&& f, Args&&... args);
};
```

## Внутреннее устройство

Очередь задач: Единая очередь std::queue<std::move_only_function<void()>> (или std::packaged_task<void()>).

Синхронизация:

* Один std::mutex для защиты очереди.
* Один std::condition_variable для усыпления/пробуждения потоков при появлении задач.

Флаг остановки: Булевый флаг stop или std::stop_token (C++20) для сигнализирования о завершении работы пула.

Основной цикл рабочего потока (Worker Loop)

1. Захватить мьютекс.
2. Ждать на condition_variable, пока очередь не станет непустой ИЛИ не взведен флаг остановки. 
3. Извлечь задачу из очереди. 
4. Освободить мьютекс.
5. Выполнить задачу.

# Усложнение 1: Децентрализация очереди (Work-Stealing)
Что меняется

Вместо единой очереди и одного мьютекса у каждого рабочего потока появляется собственная очередь задач.
Дополнительные требования

1. У каждого потока — своя очередь (Chase-Lev Deque):
* Поток-владелец добавляет задачи (push) и забирает их (pop) из хвоста очереди (LIFO/стек).
* Другие потоки при отсутствии работы забирают задачи (steal) из головы очереди (FIFO).

2. Lock-Free реализация:
* Очередь реализуется без блокировок (std::atomic с явным управлением std::memory_order).
* Поток забирает свои задачи без конкуренции с другими владельцами, обращаясь к центральному замку только при опустошении своей очереди.

3. Механизм рандомного поиска (Stealing Loop):
* Если у потока пуста своя очередь, он генерирует случайный индекс другого потока и пытается вызвать steal().
* Если все очереди пусты — поток уходит в режим ожидания (spin-wait или std::atomic::wait).

# Усложнение 2: Граф зависимостей (DAG) и C++20 Корутины
Что меняется

Отказ от blocking-ожидания результатов через std::future::get(). Вводится собственный типы Task<T> и механика co_await.
Дополнительные требования

1. Собственный Task<T>:
   * Класс-обертка над std::coroutine_handle<>.

2. Custom Awaiter (co_await integration):
   * Если вызван co_await task и task еще не готова, текущая корутина приостанавливается (suspend).
   * Поток не блокируется (не ждет на futex/condition_variable), а мгновенно возвращается в свой цикл обработки и берет другую готовую задачу из очереди.

3. Возобновление (Resume):
   * Когда зависимая задача завершается, она кладет дескриптор приостановленной корутины (coroutine_handle) обратно в пул задач для возобновления работы с места остановки.

Пояснения к этапам
* Зачем делать базовую версию первой?
Базовая версия дает отправную точку (baseline). На ней проще зафиксировать правильность управления временем жизни рабочих потоков и корректность shutdown-логики. Кроме того, на базовой версии удобно измерить падение производительности из-за lock contention при запуске миллионов мелких задач.

* Зачем нужен Work-Stealing?
Убирает contention за единственный мьютекс при большом количестве ядер. Каждый поток большую часть времени работает локально со своим кэшем L1/L2.

* Зачем нужны корутины вместо std::future?
Вызов future.get() блокирует физический поток ОС. Если у вас 8 потоков и все 8 вызовут .get(), ожидая подзадачи, пул заблокируется (thread starvation). Корутины с co_await позволяют освоить концепцию кооперативной многозадачности: вместо блокировки потока приостанавливается сама задача, а поток остается свободным.
