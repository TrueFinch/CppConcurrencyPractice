# Lock-free SPSC очередь (`SpscQueue<T, Capacity>`)

## Контекст и цель

**SPSC** (Single-Producer Single-Consumer, «один производитель — один потребитель») — очередь,
в которую пишет **ровно один** поток и из которой читает **ровно один** другой поток.
Это самая простая и самая быстрая разновидность межпоточной очереди, и именно её чаще всего
используют в HFT (High-Frequency Trading, высокочастотная торговля): поток, читающий рыночные
данные из сети, передаёт их потоку стратегии; поток стратегии передаёт заявки потоку отправки и т.д.

В задаче `ThreadSafeQueue` очередь была защищена мьютексом. Здесь мьютексов **нет вообще**:
очередь должна быть **lock-free** («без блокировок») и даже **wait-free**:

- **lock-free** — система в целом всегда продвигается вперёд: остановка (например, вытеснение
  планировщиком ОС) одного потока не может навсегда заблокировать остальные. С мьютексом это не так:
  поток, уснувший внутри критической секции, держит всех остальных.
- **wait-free** — более сильная гарантия: *каждая* операция завершается за ограниченное число шагов,
  без циклов повтора (retry loops). Для SPSC это достижимо: `tryPush`/`tryPop` — это несколько
  загрузок/записей атомиков без каких-либо циклов.

Ключевая идея: у каждого индекса ровно один «писатель».
- `tail` (куда писать следующий элемент) меняет **только** producer.
- `head` (откуда читать следующий элемент) меняет **только** consumer.

Поэтому не нужны ни мьютексы, ни CAS (compare-and-swap, атомарное «сравнить и заменить») — достаточно
атомарных `load`/`store` с правильно выбранным порядком памяти (memory order).

## Требуемый интерфейс

Каркас лежит в [SpscQueue.h](SpscQueue.h) — методы пока бросают `std::logic_error("not implemented")`.

```c++
template<typename T, std::size_t Capacity>
class SpscQueue final {
    static_assert(Capacity > 0 && (Capacity & (Capacity - 1)) == 0); // степень двойки
public:
    SpscQueue();
    ~SpscQueue();                     // уничтожает оставшиеся в очереди элементы

    SpscQueue(const SpscQueue&) = delete;   // копирование/перемещение запрещены
    SpscQueue& operator=(const SpscQueue&) = delete;

    // --- Только из потока-производителя ---
    bool tryPush(const T& value);     // false, если очередь полна
    bool tryPush(T&& value);          // при false аргумент НЕ должен быть перемещён
    template<typename... Args>
    bool tryEmplace(Args&&... args);  // конструирует элемент прямо в ячейке буфера

    // --- Только из потока-потребителя ---
    std::optional<T> tryPop();        // std::nullopt, если очередь пуста

    // --- Из любого потока ---
    static constexpr std::size_t capacity() noexcept;  // == Capacity
    std::size_t sizeApprox() const noexcept;           // приблизительный размер
    bool emptyApprox() const noexcept;
};
```

## Требования

1. **Без мьютексов и без CAS.** Только `std::atomic<std::size_t>` с `load`/`store`.
2. **Ровно `Capacity` элементов.** Очередь вмещает ровно `Capacity` элементов, а не `Capacity - 1`
   (классическая ловушка кольцевого буфера, см. подсказки).
3. **Буфер — сырая память.** `T` не обязан иметь конструктор по умолчанию. Объекты `T` должны создаваться
   только при push (placement new / `std::construct_at`) и разрушаться при pop (`std::destroy_at`)
   или в деструкторе очереди. Пустая очередь не содержит ни одного живого `T`.
4. **Move-only типы** (например, `std::unique_ptr`) должны поддерживаться.
5. **Строгая гарантия исключений (strong exception guarantee).** Если конструктор `T` бросил исключение
   в `tryPush`, очередь остаётся в прежнем состоянии.
6. **Без false sharing** (см. ниже) — `head` и `tail` должны лежать в разных кэш-линиях.

## Этапы (делайте по порядку, после каждого гоняйте тесты и бенчмарк)

### Этап 1. Корректная версия с `seq_cst`
Используйте атомики с порядком по умолчанию (`std::memory_order_seq_cst`, «последовательная
согласованность» — самый строгий и самый простой для понимания порядок). Добейтесь, чтобы прошли все тесты.

### Этап 2. Ослабление до `acquire`/`release`
Замените порядки памяти на минимально достаточные. Для **каждого** `load`/`store` письменно (в комментарии)
объясните, почему выбран именно этот порядок. Вопросы, на которые нужно ответить:
- Почему producer может читать **свой собственный** `tail` с `relaxed`?
- Почему запись `tail` producer'ом должна быть `release`, а чтение `tail` consumer'ом — `acquire`?
  Какое отношение **happens-before** («происходит-до») это устанавливает и какие данные оно «публикует»?
- Зачем consumer'у публиковать `head` через `release`, если он ничего «не передаёт» producer'у?
  (Подсказка: подумайте о том, что producer **перезапишет** ячейку, из которой consumer ещё,
  возможно, читает.)

Термины:
- `relaxed` — гарантирует только атомарность самой операции, никакого упорядочивания с другими операциями.
- `release` (на записи) — все записи текущего потока, сделанные *до* неё, станут видны тому,
  кто прочитает это значение с `acquire`.
- `acquire` (на чтении) — пара к `release`: после такого чтения видны все записи, «опубликованные» release'ом.

### Этап 3. Устранение false sharing
**Кэш-линия** — минимальная порция памяти (обычно 64 байта на x86), которой процессорные ядра обмениваются
между своими кэшами. **False sharing** («ложное разделение») — ситуация, когда две *разные* переменные,
которые пишут разные потоки, оказались в одной кэш-линии: ядра вынуждены постоянно отбирать эту линию
друг у друга, хотя логически ничего не делят.

Разнесите `head` и `tail` по разным кэш-линиям через
`alignas(std::hardware_destructive_interference_size)` (или явно `alignas(64)`). Измерьте разницу бенчмарком.

### Этап 4. Кэширование индексов (главная HFT-оптимизация)
Даже без false sharing каждый `tryPush` читает `head` (который пишет другое ядро), а каждый `tryPop` —
`tail`. Каждое такое чтение — потенциальный **cache miss** (промах кэша, ~десятки наносекунд на перенос линии
между ядрами).

Идея: producer хранит **локальную копию** `head` (`cachedHead`) в своей кэш-линии и перечитывает настоящий
`head` только когда по кэшированному значению очередь *кажется* полной. Симметрично consumer хранит
`cachedTail`. Реализуйте и снова измерьте. Подумайте: почему устаревшее (stale) значение кэша
**безопасно**? (В какую сторону оно может «врать»?)

### Этап 5 (опционально)
- Добавьте пакетные операции `tryPushBulk`/`tryPopBulk`.
- Соберите тесты с ThreadSanitizer (`-fsanitize=thread`) в WSL под Clang/GCC и убедитесь, что
  гонок нет. Специально «сломайте» один `acquire` → `relaxed` и посмотрите, поймает ли его TSan.
  Обратите внимание: на x86 тесты, скорее всего, всё равно пройдут — x86 имеет сильную модель памяти
  (TSO), и большинство ошибок с порядком памяти проявляются только на ARM. Именно поэтому
  обоснование порядков в Этапе 2 важнее зелёных тестов.

## Подсказки по кольцевому буферу (ring buffer)

- Вместо индексов в диапазоне `[0, Capacity)` храните **монотонно растущие счётчики** `head` и `tail`
  (типа `size_t`, переполнение за разумное время невозможно). Тогда:
  - размер = `tail - head`;
  - пусто ⇔ `tail == head`;
  - полно ⇔ `tail - head == Capacity`;
  - позиция в буфере = `counter & (Capacity - 1)` — именно поэтому `Capacity` степень двойки
    (побитовое И вместо дорогого деления по модулю).
- Так вы автоматически избегаете «ловушки `Capacity - 1`», когда одна ячейка тратится впустую,
  чтобы отличать «пусто» от «полно».
- Сырое хранилище: `alignas(T) std::byte storage[Capacity][sizeof(T)]` или массив
  `union { T value; }` — выберите и объясните выбор.
